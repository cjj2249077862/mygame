# RaidDeck 代码开发规范

本规范适用于现有 Godot 4 / GDScript 工程的增量开发，涵盖代码编写、Demo 迁移、新内容接入和验收。玩法以《开发规格确认稿》中标为“已确认”的结论为准。实现遇到同一条目中仍待定的玩法细节时，先确认该行为，再开发依赖它的部分。[开发规格确认稿](./开发规格确认稿.md)

定稿时的 Demo 有 5 个游戏脚本和 1 个主场景。下列文件清单、模块职责和用例是基础战斗、配表与 UI 拆分阶段的交付目标。工程当前声明 Godot 4.7 特性，最终使用的小版本随工程与导出环境核定。[工程配置](../../project.godot)

## 1. GDScript 编写与变更

- 使用 Tab 缩进。类名用 `PascalCase`，脚本文件名、函数、变量和信号用 `snake_case`，常量和枚举成员用 `UPPER_SNAKE_CASE`。内部方法以 `_` 开头，信号回调用 `_on_`。
- 新增公共方法声明参数与返回类型。名称应说明对象或动作，例如用 `caster_id` 标明实际施放者。注释优先记录结算顺序、取整依据、数据兼容或其他仅凭代码难以看出的约束。
- 核心战斗逻辑可脱离场景树运行。修改公共方法、信号或配置字段时，同步检查调用方、读取方和受影响的用例。一次变更围绕一个明确目标。
- Godot 的 `.gd.uid` 随相应脚本提交。缓存和导出产物按项目忽略规则处理。[项目忽略规则](../../.gitignore)

## 3. 模块职责与状态归属

| 模块 | 持有的状态与职责 |
| --- | --- |
| Main | 创建并连接本局流程和界面，按冒险状态展示战斗、奖励或结算页。先接好信号再开始冒险，保证首次开局也能显示初始状态。 |
| RunManager | 管理本局牌组、跨战斗进度、玩法随机进度及已生成的奖励。接收战斗结果，决定发奖、进入下一节点或结束冒险。领取时核对候选 ID，跳过选牌时维持牌组。两种操作都只能结算一次。 |
| BattleEngine | 管理本场手牌、抽弃牌堆、能量、单位状态、敌方意图和胜负。对外提供合法施放者、合法目标与预览查询，并接收出牌和结束回合操作。 |
| 效果与事件 | `effect_resolver.gd` 执行可复用的基础效果。`battle_events.gd` 按确定顺序通知被动与遗物。一次操作及其连锁完成后，再按序向界面呈现结果；快放和动画回调均不得改变战果。 |
| BattleView | 协调手牌、单位和日志控件，保存选牌、施放者、悬停目标与演出锁等临时状态。取消、换回合或离开战斗时清理选择；手牌变化后重新核对选中的副本。 |
| 手牌、单位、日志、奖励面板 | 用传入的数据渲染界面，以信号上报点击。奖励面板展示 RunManager 已生成的候选，上报所选卡牌 ID 或跳过请求。重绘、关闭再打开或恢复待领奖状态时，展示同一批候选。 |
| GameData | 加载并校验运行时 JSON，按稳定 ID 提供定义。当前生命、卡牌副本的升级状态等运行时数据由战斗或本局模型持有。 |

出牌时，核心入口先校验阶段、手牌、费用、实际施放者和目标，再扣能量、移动卡牌并结算效果。拒绝操作时给出可供界面显示的原因，保证手牌、能量、弃牌堆和目标状态均保持调用前的值。按钮禁用、目标高亮、预览和实际出牌共用核心判断。预览只读取状态，不消耗资源、不推进随机进度。

### 从现有 main.gd 迁移

1. **先迁出战后流程。** 从 `_on_battle_ended()` 接走通关判定、候选生成、领取和推进。一并梳理 `BattleEngine` 中的 `master_deck`、`stage_index` 与开局入口，使本局牌组和进度只有一处维护。先保留现有弹窗验证完整流程。
2. **再统一出牌判断。** 将按钮及 `_on_unit_clicked()` 里的资格判断收进核心，由现有界面先使用新入口。验证敌方目标牌选中友方时被拒绝，取消后资源和手牌保持原值。
3. **最后拆场景和控件。** 将 `_build_ui()` 的固定布局移入场景，将 `_refresh_ui()` 的手牌和单位渲染交给对应控件。`_on_log_added()` 的文本显示移入日志面板，`_on_battle_ended()` 的候选按钮移入奖励面板。由战斗视图协调战斗输入。从主场景走通选牌、结束回合、领奖和重开，验证重开后一次点击只触发一次操作。

现有奖励抽取位于 UI，当前核心按职业查找首个存活施放者。迁移这两个入口时须同时核对 UI 与核心的调用方。[Demo 主界面](../../scripts/ui/main.gd) · [Demo 战斗引擎](../../scripts/core/battle_engine.gd)

## 4. 配置、文案与 Demo 硬编码迁移

日常编辑以 XLSX 为源，使用导出工具一键校验并生成同名 JSON，游戏读取 JSON。卡牌、角色等使用稳定 ID，显示名称可以独立修改。

| 内容 | 维护方式 |
| --- | --- |
| 卡牌、初始牌单、敌人、遭遇、奖励池和可调数值 | 在对应源表登记。费用、基础伤害、治疗量、倍率和抽牌数等可调值各维护一处。机制的计算顺序、目标选择和取整规则在核心代码实现。 |
| 卡名、角色名、按钮、操作提示和胜负提示 | 在中文文案表使用稳定键，例如 `ui.end_turn`。卡牌、角色和界面通过键引用对应文字。 |
| 卡面、预览和战斗日志 | 卡面以命名占位符读取配置的基础值。预览读取针对当前施放者和目标的核心计算结果。玩家可见日志由事件和实际结算值填充文案模板。 |
| 程序常量与界面样式 | 枚举、索引哨兵等程序语义保留在脚本。可复用的字号、颜色、间距归入主题，页面特有的布局和尺寸归入相应场景。 |

导出和加载都须检查重复 ID、缺失引用、字段类型和范围、升级关系、效果类型及适用目标。文案键、命名占位符和参数必须对应。校验错误应定位到源表、行和字段，并阻止错误配置生效；导出的数据须保留足够的来源信息供加载时定位问题。

**配表迁移顺序。** 先选「快速治疗」跑通源表、导出、加载、卡面、预览和日志，再迁移其余卡牌、角色与敌人、遭遇、回合参数和奖励池，最后清理界面提示及旧日志。每批切换后移除对应的旧定义。待初始牌组、战斗和奖励等所有调用方均使用 GameData 后，移除 `card_db.gd`。

**改表验收。** 在验证数据中把「快速治疗」的基础治疗量从 14 改为 18，仅修改该源表单元格并重新导出。卡面应显示“最多 18 点”。对缺血 20 点和 2 点的目标，实际分别恢复 18 点和 2 点；在治疗仇恨系数 0.4、无其他修正的条件下，分别产生 7 点和 1 点仇恨。预览、生命变化和日志应一致。

## 5. 扩展卡牌与角色

### 新增一张卡牌

1. 在 `cards.xlsx` 主表新增一条定义，填写 `card_id`、费用、稀有度、施放资格、目标类型、获取来源和文案键。效果工作表按顺序登记操作及参数。例如「盾牌猛击」依次执行 `damage`、`interrupt`。
2. 升级配置关联同一基础卡 ID。牌组允许同名副本；单次升级记录在选中的副本上。卡名和描述模板进 `texts_zh_cn.xlsx`，需要新卡图时填写素材引用。
3. 导出并验证施放资格、效果顺序、升级和显示。复用已有机制时，典型改动为 2 份源表、2 份自动更新的 JSON、0～1 张新卡图，新增脚本和场景均为 0。遇到无法组合表达的新效果时，为公共效果处理增加实现及规则用例，供后续卡牌复用。

### 新增一名角色

1. 在 `characters.xlsx` 以唯一 `character_id` 登记职业 `role_id`、基础属性、立绘和已确定的解锁条件。在关联工作表填写该角色的固定初始牌单和专属被动。初始卡牌按配置数量组成全队共享牌组。
2. 职业基础卡关联 `role_id`，角色专属卡关联 `character_id`，通用战术牌可由任一存活队员施放。新增专属卡时更新 `cards.xlsx`，角色名、被动和专属卡的文字进入文案表。
3. 出牌指令携带实际施放者 `caster_id`。只有一人符合资格时自动选定，多人符合时由玩家选择。基础效果按定义指向该施放者或选定目标。已有事件与效果可以组合配置，新触发时机才扩展事件处理及相应用例。
4. 用两名同职业角色同时上阵验收。两人都可施放职业基础卡，专属卡只允许对应本人施放；选中第二名角色后，其自施护盾和应得仇恨应正确归属。两人复用同一单位视图。

使用已有机制时，新增角色的典型改动为 2～3 份源表、相应的导出 JSON、立绘及所需卡图，新增脚本和场景均为 0。角色名单、具体解锁条件和卡牌内容量按玩法确认稿逐项确定。

## 6. 随机、存档与交付验收

- 核心管理影响玩法的随机过程。存档保存随机进度、已生成的地图、奖励等内容以及牌堆顺序。同一存档执行相同操作序列，结果应可复现。
- 局内进度、永久进度和设置分别保存，记录存档版本。写入失败须保留原文件，保留最近有效备份供损坏恢复。恢复存档遵守已确认的结算时点。
- 核心规则以无头用例断言。除正常出牌外，覆盖非法目标、能量不足、双同职业施放归属等与改动相关的边界。选牌后结束回合，再点击目标，应无法误打新手牌。
- 冒险流程覆盖普通胜利、最终胜利、失败重开、领取和跳过奖励。普通胜利后重绘面板应显示相同候选，连续点击只入组一张、推进一次。跳过选牌后牌组保持原值，金币照常发放，奖励流程只推进一次。最终胜利直接进入通关结算。地图和存档改动须验证退出与恢复后的结果。
- 交互改动从 `scenes/main.tscn` 进入实测；阶段验收结合规则测试、地图与存档回归、完整流程试玩和可复现批量模拟。模拟场次与回合上限可配置，异常保留随机种子与日志。
- 交付记录写明验证入口、观察到的结果及仍待验证的项目。需编译或重启时，沿用项目约定由用户手动执行。
