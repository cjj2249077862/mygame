## 1. 结论

**当前 HEAD 不能判定为可运行，更不能判定为第二阶段验收通过。** 与前一阶段不同，这次的问题不是“设计风险”或“测试覆盖不足”，而是三个直接阻断：

1. **主场景无法编译。** `run_manager.gd` 的 `_event_details()` 存在 GDScript 类型推断错误，`main.gd` 及所有依赖 `RunManager` 的界面/测试都无法加载。游戏从 `scenes/main.tscn` 启动会直接失败。
2. **读档链路被 JSON 数字类型与 Godot 的严格 `in` 比较共同打断。** 有效战斗快照写入后，从 JSON 读回时 `phase` 变成 `1.0`，而 `1.0 in [1]` 在 Godot 中为 `false`；`_valid_snapshot()` 和 `BattleEngine.can_restore()` 因此会把合法存档判为损坏。即使修掉编译错误，Continue、战斗恢复和终局补记仍不可用。
3. **Boss 炸弹会让自动存档失败并锁住玩法。** `apply_bomb()` 用 `mark.remaining = ...` 这类属性赋值，给字典新增了 `StringName` 键；`_serializable()` 只接受 `String` 键，于是任何带炸弹的战斗快照都被判定不可序列化。`_checkpoint()` 校验失败，`persistence_error` 锁住出牌，第一章 Boss 战无法正常继续/退出/续玩。

在对临时副本做了“显式类型、阶段转 int、炸弹键改字符串、meta 归一化、地图弹窗尺寸、意图数值归一化”等最小修复后，绝大多数测试恢复通过，整章模拟 32 个种子完成 27 局、失败 5 局；这说明核心实现已接近可用，但**当前提交本身并不具备这些修复**。

结论分级：

- **P0（阻断）**：编译错误、读档被拒、Boss 炸弹存档失败。
- **P1（重要）**：章节地图弹窗实际只有约 98×94、JSON 类型漂移导致多处测试失败、测试用例自身存在误报/错判。
- **P2（一般）**：合法性校验缺口、候选不足时的商店空位、遗物权重、未知遭遇/负治疗等防御性边界。
- **P3（建议）**：提示文案噪音、地图单节点对齐、测试失败信息误导等。

与前一阶段审核相比，事件/遗物统一注册、预览对状态与 RNG 的克隆、奖励回执后的面板重绘、self+dispel 的共同状态选择入口、UI 尺寸用例显式设置逻辑视口等，均已有对应实现；本次阻断主要来自第二阶段新增的存档/地图 UI/内容扩展代码，而不是第一阶段遗留问题。

## 3. 主要发现

### 3.1【P0｜阻断】`run_manager.gd` 类型推断错误导致主场景无法编译

位置：[run_manager.gd](../../scripts/core/run_manager.gd:817)

```gdscript
var description := (
    data.text("run.event.leave") if benefits.is_empty() else "；".join(benefits)
)
```

`data` 声明为 `RefCounted`，`data.text()` 的返回类型对编译器是 `Variant`；分支的另一侧是 `String`，GDScript 4.7 无法为该条件表达式推断统一类型，直接报 `Cannot infer the type of "description"`。

影响：

- `run_manager.gd` 编译失败；
- `main.gd` 依赖它，主场景不可加载；
- `test_run_flow`、`test_chapter_flow`、`test_battle_ui`、`test_chapter_ui`、`test_battle_sim` 全部无法正常执行；
- 用户从 `scenes/main.tscn` 启动会失败，不涉及任何玩法逻辑。

建议：

- 改为 `var description: String = (...)`；
- 在静态验收入口中增加真正的 Godot 编译检查，不能只依赖 `gdtoolkit`。可以逐个脚本执行 `godot --headless --check-only --script ...`，并扫描 `SCRIPT ERROR|Parse Error|Compile Error`；由于 `--check-only` 在解析失败时退出码仍为 0，必须结合日志判定；
- 更稳妥的是执行一次 `godot --headless --editor --import`，再运行一个最小主场景冒烟用例。

### 3.2【P0｜阻断】JSON 数字变成浮点，阶段判断使用严格 `in`，合法存档被判损坏

位置：

- [battle_engine.gd](../../scripts/core/battle_engine.gd:158)
- [run_manager.gd](../../scripts/core/run_manager.gd:1210)
- [run_manager.gd](../../scripts/core/run_manager.gd:1095)
- [run_manager.gd](../../scripts/core/run_manager.gd:1464)
- [run_manager.gd](../../scripts/core/run_manager.gd:1294)
- [run_manager.gd](../../scripts/core/run_manager.gd:1299)

现状与根因：

Godot 4 的 `JSON.parse_string()` 把所有数字解析为 `float`。`SaveManager` 用 JSON 文本保存 payload，因此 `run`、`battle`、`meta` 读回后，`phase`、`turn`、`hp`、`copy_id` 等整数字段全部是 `1.0` 这样的浮点。Godot 的 `Array.has/in` 对数字使用严格同类型比较：

```text
1.0 == 1      -> true
1.0 in [1]    -> false
```

审核中用无头探针复现：

```text
初始合法战斗快照：can_restore(snapshot) = true
JSON 往返后：      can_restore(decoded)  = false
phase = 1（int），decoded.phase = 1.0（float）
```

具体命中点：

- `battle_engine.gd:158`：`saved.get("phase", -1) not in [PLAYER, WON, LOST]`，JSON 读回的 `1.0` 不在整型枚举数组中，`restore()` 直接返回 false。`test_boss_rules` 的第 2 条断言即此路径。
- `run_manager.gd:1210`：`candidate.phase not in ACTIVE_PHASES + [...]`，JSON 读回的任何 run 都会被 `_valid_snapshot()` 判为非法；`SaveManager.read_slot("run", _valid_snapshot)` 因此返回空，Continue 必然失败。
- `run_manager.gd:1464`：`candidate.phase not in ACTIVE_PHASES`，在修掉 1210 后仍会把有效活动存档误判为终局，继而要求 `result`，失败。
- `run_manager.gd:1294`、`1299`：`candidate.phase in node_phases.values()`、`candidate.phase in [BATTLE, REWARD]` 同样因浮点恒为 false，导致阶段与节点类型校验被**静默跳过**；这不是拒绝，而是降低校验强度，属于同一根因。
- `run_manager.gd:1095`：`_reconcile_terminal_record()` 的 `saved.phase in ACTIVE_PHASES` 也会把活动存档当成终局；修掉校验后，启动时会走 `_record_result()` 并 `phase = IDLE` 的错误分支。

后果：

- 战斗中自动保存的存档无法通过读取校验；`Continue` 不可用，`has_saved_run()` 会把合法存档当“活动/损坏”处理，新开局还会要求先放弃旧局。
- 即使绕开 `RunManager` 的校验，`BattleEngine.restore()` 仍会拒绝 JSON 往返快照，中途退出后的战斗恢复不可用。
- 与 3.3 叠加时，Boss 战甚至连“写入”都无法通过 `_checkpoint()` 的自校验。

建议：

- 在数据进入校验前统一归一化：对 `phase` 等已知整型字段使用 `int(value)`；或让 `SaveManager` 接受一个显式的反序列化/归一化回调。
- 把 `_valid_snapshot()` 中所有 `phase in ...`、`BATTLE/REWARD` 判断改为 `int(candidate.phase)`（`_reconcile_terminal_record()` 同理）。
- 补一个 JSON 往返回归：`snapshot → JSON.stringify → JSON.parse_string → _valid_snapshot/restore` 必须与内存快照等价；测试 `battle_engine` 和 `run_manager` 两层。
- 不要用“`1.0 == 1` 为 true”来推断 `in` 也 true；Godot 的数组成员判断是严格类型比较。

### 3.3【P0｜阻断】炸弹标记的 `StringName` 键使战斗快照不可序列化，Boss 战自动存档失败

位置：[battle_engine.gd](../../scripts/core/battle_engine.gd:1066)、[battle_engine.gd](../../scripts/core/battle_engine.gd:1080)

现状：

```gdscript
if mark.is_empty():
    mark = {"id": int(state.next_mark_index), "kind": "bomb", "source_id": source.id}
    ...
mark.remaining = duration
mark.first_tick_turn = int(state.turn) + 1
mark.amount = amount
```

GDScript 的 `dict.key = value` 对**新键**使用 `StringName`。审核探针显示：

```text
mark key=id              type=4  (String)
mark key=kind            type=4  (String)
mark key=source_id       type=4  (String)
mark key=remaining       type=21 (StringName)
mark key=first_tick_turn type=21 (StringName)
mark key=amount          type=21 (StringName)
```

而 `_serializable()`（[battle_engine.gd](../../scripts/core/battle_engine.gd:415)）要求字典键必须是 `String`：

```gdscript
if value is Dictionary:
    for key in value:
        if not key is String or not _serializable(value[key]):
            return false
```

因此：

- `can_restore()` 对**内存中**带炸弹的快照返回 false；`_valid_snapshot()` 也随之失败；
- `_checkpoint()` 写档时 `saves.write_slot(..., _valid_snapshot)` 先做校验，返回 `save_corrupt_or_incompatible`；
- `persistence_error` 被设置，`battle.external_block_reason = "error.save"`，出牌/结束回合被锁；玩家在 Boss 第一次挂弹后的下一个动作就会遇到“保存失败”，既不能安全继续，也不能正常退出续玩。

审核证据：

- 直接用 `BattleEngine` 启动 `outpost_iron_throne`，`apply_bomb()` 后 `can_restore(snapshot()) = false`；仅把三个属性赋值改成字符串键后，内存快照即可通过。
- 修复前 `test_battle_sim` 的 32 个种子全部在到达 Boss 后报 `invalid_checkpoint`；修复后 32 个种子全部通过，27 局完成第一章、5 局失败。

建议：

- 改用 `mark["remaining"] = ...`、`mark["first_tick_turn"] = ...`、`mark["amount"] = ...`，保证键类型稳定；
- 更根本地，让 `_serializable()` 接受 `StringName` 并在快照/校验前统一归一化，避免未来任何 `dict.new_key = ...` 再次触发同类问题；
- 增加“带炸弹快照可通过 `_valid_snapshot`、可写入、可 JSON 往返恢复”的回归用例；
- 该问题不需要人工试玩即可判定为阻断，因为它发生在自动保存路径上。

### 3.4【P1｜用户可见】章节地图弹窗实际只有约 98×94，路线节点全部溢出

位置：[main.gd](../../scripts/ui/main.gd:262)、[main.gd](../../scripts/ui/main.gd:278)

现状：

```gdscript
_on_main_resized()
$ChapterMap.popup_centered($ChapterMap.size)
```

```gdscript
if $ChapterMap.visible:
    $ChapterMap.size = window_size
    $ChapterMap.popup_centered()
else:
    $ChapterMap.size = window_size
```

`popup_centered()` 会把窗口重置为其内容最小尺寸；在 `AcceptDialog` 上，这个最小尺寸约为 `98×94`。代码把目标尺寸作为参数传入或在 popup 之前设置，都会被随后重置。审核在无头 UI 测试中观察到：

```text
MAPDBG size=(1280, 800) dsize=(98, 94) inner=[P:(-1,-1), S:(100,96)]
MAPDBG size=(1440, 900) dsize=(98, 94) inner=[P:(-1,-1), S:(100,96)]
```

而地图节点按钮宽度 180、合计 24 个节点，全部落在负坐标/弹窗之外；`test_chapter_ui` 的 “All ten map depths fit the overview” 因此连续失败 48 次。把 `popup_centered()` 改为“先 popup，再显式 `$ChapterMap.size = window_size`”后，两个逻辑尺寸下弹窗均为 `1180×740`，该组断言全部通过。

影响：

- 新开局立即弹出的“整章路线”实际不可读，玩家无法按第 18 项规划路线；
- 这是当前首批玩家会看到的第一屏之一，属于明显的可玩性缺陷。

建议：

- 在 `_on_main_resized()` 的可见分支改为 `popup_centered(); $ChapterMap.size = window_size`；
- 在 `_on_chapter_map_pressed()` 中同样在 popup 之后设置尺寸，或抽出统一的 `_fit_chapter_map()`；
- 保留现有 UI 用例，并补“弹窗打开后改变逻辑视口仍能重排”的断言。

### 3.5【P1｜存档一致性】JSON 往返造成类型漂移，多处测试失败信息具有误导性

#### 3.5.1 永久统计 meta 未归一化

位置：[run_manager.gd](../../scripts/core/run_manager.gd:68)、[test_save_manager.gd](../../tests/test_save_manager.gd:28)、[test_chapter_flow.gd](../../tests/test_chapter_flow.gd:705)

- `RunManager._restore_fields()` 用 `_restore_numbers()` 处理了本局字段，但 `_init()` 读取 meta 时直接 `meta = loaded`，没有归一化。
- 因此 `Run.new(...).meta` 的计数是 `1.0`，内存中是 `1`；`meta == meta_before` 为 false。
- `test_chapter_flow` 的 12 条失败中，8 条被命名为 “Reload cannot increment statistics twice”，实际原因并不是重复计数，而是 **int/float 类型不等**；另有 “Terminal repair is idempotent” 等同类失败。把 `meta = _restore_numbers(loaded)` 后，该套 402 条断言全部通过。
- `SaveManager` 是通用 JSON 存取层，`read_slot("run") == first` 在 [test_save_manager.gd](../../tests/test_save_manager.gd:28) 失败也是同一原因：JSON 无法保留 `int` 类型。

建议：

- 在 meta 读入后统一归一化，或在 `_valid_meta()` 前做类型转换；
- 对 `SaveManager` 明确契约：它是“JSON 值的无损字符串/浮点往返”，不承诺整数类型；测试应做语义比较，或提供一个带 schema 的读取方法；
- 不要根据 “Reload cannot increment statistics twice” 的失败文案去改统计逻辑，那不是根因。

#### 3.5.2 战斗意图数值在 restore 时单方面转为 int

位置：[battle_engine.gd](../../scripts/core/battle_engine.gd:141)

`restore()` 把 `intent.hits/stacks/order` 转成 `int`，但新战斗从 GameData（JSON 加载）拿到的这些字段是 `float`。于是：

```text
保存时：intent.hits = 1.0, order = 2.0, stacks = 2.0
恢复后：intent.hits = 1,   order = 2,   stacks = 2
```

`test_chapter_ui` 的 “Continue restores the last complete turn, not an opening battle” 因为 `battle.snapshot() == saved` 的严格字典比较而失败；这不是玩法差异，而是恢复后的状态与保存前不等价。把转换去掉（或在创建意图时统一转 int）后，该套 213 条断言通过。

建议：

- 选一个边界统一：要么创建意图时就把数值归一化为 int，要么 restore 完全保留原类型并让规则层显式 `int()`；
- 补“保存→恢复→再保存”的幂等断言，而不只是“能恢复”；
- 同类问题也适用于 `intent.amount`（当前 restore 未转换，若未来改成 int 需同步测试）。

### 3.6【P1｜测试可信度】测试自身存在误报与错判

位置：[test_suite.gd](../../tests/test_suite.gd:24)、[test_battle_ui.gd](../../tests/test_battle_ui.gd:315)、[test_battle_ui.gd](../../tests/test_battle_ui.gd:425)、[test_save_manager.gd](../../tests/test_save_manager.gd:28)

1. **脚本错误不会让 Suite 失败。** `_run_suite()` 只检查 `assertion_count` 和 `failures`；解析错误、`Invalid call`、`Nonexistent function` 等不会进入 `failures`。因此当前 HEAD 的 `test_battle_rules` 只执行 5 条断言仍打印 `passed:true`，`test_battle_sim` 只执行 3 条也打印 `passed:true`。验收包装脚本的 `ERROR_LINE` 能兜底，但直接跑 Suite 的退出码/标记不可信，CI 或人工可能误判。
2. **`test_battle_ui.gd:315`** 把未类型化数组传给 `RunManager.start(seed, lineup: Array[String])`，Godot 4.7 直接报 “array argument does not have the same element type”。这一处错误导致同一用例的 10 条断言失败（包括“群体卡施放者”“群体护盾”“复活目标”），这些不是 UI 逻辑缺陷。测试应显式 `var lineup: Array[String] = [...]`，或接口放宽为 `Array`。
3. **`test_battle_ui.gd:425`** 断言 `view.engine.settled.get_connections().size() == 1`，但该信号同时连接了 `RunManager._on_battle_settled`（保存）和 `BattleView._on_settled`（演出），正常就是 2。测试应只统计 view 的 Callable，或改为验证没有重复的 view 连接；不要为了让它变 1 而删掉保存连接。
4. **`test_save_manager.gd:28`** 的严格字典相等与 JSON 数字类型不兼容，见 3.5.1。

建议：

- 在 Suite 层增加“运行时错误/空断言/最少断言数”的自检，或规定所有验收只能走 `accept_phase_two.py`；
- 修正上述三处测试，并在测试失败信息中附实际差异，而不是只写语义假设；
- 让 `--static-only` 至少执行一次真正的 Godot 编译检查，避免“静态通过、引擎一跑就编译失败”。
