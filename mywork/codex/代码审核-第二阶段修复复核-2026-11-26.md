## 4. 主要发现

### 4.1【P1｜验收阻断】`test_chapter_flow` 编译错误，新增回归套件完全没有执行

位置：[test_chapter_flow.gd:113](../../tests/test_chapter_flow.gd:113)

```gdscript
var before := run.battle.snapshot()
```

`run` 声明为 `RefCounted`，`battle` 是动态属性，`snapshot()` 的返回值对编译器是 `Variant`；`:=` 无法推断，GDScript 4.7 报 Parse Error。后果：

- `test_chapter_flow` 0 条断言执行，完整入口 `nonzero_exit`；
- 本轮新增的 `_test_json_checkpoint_types`、`_test_bomb_checkpoint_round_trip`、空商品位、事件回执、终局保存失败等用例**全部未纳入本轮验收**；
- 静态检查（gdtoolkit 解析/格式）发现不了这类类型推断错误，12:26 的 `status: pending_engine` 静态报告因此看起来是“通过”的。

建议：

- 改为 `var before: Dictionary = run.battle.snapshot()`；
- 在静态验收入口增加真正的 Godot 编译检查（逐脚本 `--check-only` 并扫描日志，或完整 `godot_import` + 最小主场景冒烟），不能把 gdtoolkit 解析通过写成“引擎类型检查通过”；
- 每次新增/修改 GDScript 测试后至少运行一次完整入口，不能只做静态检查。

#### 4.1.1 仅修语法后，`test_chapter_flow` 仍有 5 条失败，但根因是测试的浮点精确比较

在临时副本中只把 113 行改成显式 `Dictionary` 后，`test_chapter_flow` 执行 630 条断言，出现 5 条失败，全部来自 `_reload()` 的严格比较：

```text
stable/result/elapsed_seconds: 0.31999999999999995 / 0.32000000000000001
meta/records[0]/elapsed_seconds: 0.31999999999999995 / 0.32000000000000001
JSON 两边都是 "0.32"
```

内存中 `elapsed_seconds` 由 `毫秒 / 1000.0` 计算得到，JSON 写出 `0.32` 后读回是另一个最接近的 double，差 1 ulp。`_stable()` 只删了顶层 `elapsed_seconds`，没有处理 `result.elapsed_seconds` 和 `meta.records[].elapsed_seconds`；Godot 的 `Dictionary ==` 对浮点值做精确比较，因此失败。失败文案仍写成 “Reload cannot increment statistics twice”，容易再次被误诊为统计重复。

这不是玩法缺陷，而是测试契约问题：

- 若坚持 `elapsed_seconds` 保持浮点（施工记录已明确），测试必须按语义比较（例如屏蔽时间字段或 `is_equal_approx`）；
- 或把存档时间改为整数毫秒，使 JSON 往返精确；但这会改变存档字段语义，需要版本/契约说明；
- 失败信息应附实际差异，不应只写“不能重复计数”。

### 4.2【P1｜用户可见】章节地图/查看/选择弹窗的居中算法使用了瞬态尺寸，窗口变化时弹窗跑到左上或屏幕外

位置：

- [main.gd:307](../../scripts/ui/main.gd:307) `_popup_sized()`
- [node_panel.gd:228](../../scripts/ui/run/node_panel.gd:228) `_fit_picker()`

现状：

```gdscript
dialog.popup_centered()
var center: Vector2i = dialog.position + dialog.size / 2
dialog.size = window_size
dialog.position = center - dialog.size / 2
```

问题在于 `popup_centered()` 之后立即读取 `dialog.size` 不可靠：在嵌入子窗口模式下，`popup_centered()` 会按“目标尺寸/上一次尺寸”计算位置，但 `dialog.size` 这一帧仍可能读到内容最小尺寸 98×94；随后代码用这个混合状态计算中心，再设置新尺寸，中心自然错位。测试中实际观测：

| 场景 | 期望中心 | HEAD 实际可见位置/尺寸 | 中心偏差 |
| --- | --- | --- | --- |
| 1440×900 首次打开 | (720,450) | (129,77) / 1180×740 | 约 3.6px |
| 1280×800 逻辑视口 | (640,400) | (0,36) / 1180×740（代码先算出 (-491,-287)，被嵌入窗口夹到左上） | 横向 50px、纵向 6px |
| 1200×760 逻辑视口 | (600,380) | (0,36) / 1160×720（代码先算出 (-521,-277)） | 横向 20px、纵向 16px |
| 1200 后回到 1440 重新打开 | (720,450) | **(-411,-243)** / 1180×740 | 大部分在视口外 |

其中 1440 重新打开的场景就是 `test_chapter_ui` 的 `The chapter overview stays inside the logical viewport` 失败来源；`Resizing the popup keeps it centred` 在首次打开和每次 resize 后都失败。

修复验证（临时副本）：

```gdscript
dialog.popup_centered()
var viewport_center: Vector2i = Vector2i(get_viewport_rect().size) / 2
dialog.size = window_size
_center_popup.call_deferred(dialog, viewport_center)  # 嵌入窗口在尺寸变化后可能再次被定位
```

`_fit_picker()` 同样应先取视口中心，尺寸设置后 deferred 再应用位置；当前 `test_chapter_ui` 只检查 Picker 的尺寸和边界，没有检查中心，所以该路径没有被覆盖。与 4.3 的地图节点定位修复一起应用后，`test_chapter_ui` 414/414 通过。

需要说明的验收口径：

- 项目使用 `canvas_items` + 基准视口 1440×900。真实物理窗口缩放到 1200×760 时，`get_viewport_rect()` 仍是 1440×900（临时探针确认），弹窗按逻辑坐标缩放。测试里的 `_set_logical_size()` 是直接改 `content_scale_size`，得到的是“另一种基准视口”，不是物理最小窗口。
- 因此，当前固定 1440×900 逻辑视口下，首次打开约 3px 偏移；1280/1200 逻辑视口下横向偏 50/20px、纵向偏 6/16px，1440 重开后的完全跑偏，都是本轮无头用例实际观察到的。物理窗口缩放不会改变逻辑视口，但同样会触发 `Main.resized` 并进入 `_popup_sized()`；其实际屏幕表现需在带窗口环境复核，不能仅凭固定视口推断无影响。
- 但 `_on_main_resized()` 在**任何** Main 尺寸变化时都会走这条路径；定位算法本身是错误的，不能因为当前拉伸模式暂时不暴露就保留。建议同时修正测试口径：要么明确支持可变逻辑视口并保留这些用例，要么用固定容器/真实窗口缩放验证最低物理窗口，不能把 `content_scale_size` 用例当成“最低窗口已验收”。

### 4.3【P1/P2｜验收失败但视觉影响较小】章节地图最后一层节点超出画布 4px

### 4.4【P1｜存档健壮性】`meta` 槽损坏会让游戏无法开始、放弃、重试或退出

位置：

- [run_manager.gd:63](../../scripts/core/run_manager.gd:63) `_init()` 读取 `meta`
- [run_manager.gd:74](../../scripts/core/run_manager.gd:74) `start()`
- [run_manager.gd:419](../../scripts/core/run_manager.gd:419) `abandon_run()`
- [run_manager.gd:467](../../scripts/core/run_manager.gd:467) `retry_save()`
- [run_manager.gd:406](../../scripts/core/run_manager.gd:406) `return_to_menu()`
- [run_manager.gd:1065](../../scripts/core/run_manager.gd:1065) `_checkpoint()`
- [main.gd:140](../../scripts/ui/main.gd:140) `_on_quit()`

复现（临时副本，HEAD 产品代码未改）：

```text
persistence=save_corrupt_or_incompatible slot=meta phase=0
start=false
abandon=error.save
retry=false error=save_corrupt_or_incompatible
return_to_menu=false
```

链路：

1. `_init()` 读 `meta` 失败 → `persistence_error` 有值、`_load_error_slot = "meta"`；
2. `start()` 因 `persistence_error != ""` 拒绝新局；
3. `abandon_run()` 对 `_load_error_slot == "meta"` 直接返回 `error.save`；
4. `retry_save()` 重新读取同一个损坏文件，继续失败；
5. `return_to_menu()` 在 `persistence_error != ""` 时调用 `_checkpoint()`，而 `_checkpoint()` 在 `_load_error_slot != ""` 时直接返回 false，因此永远无法返回菜单；
6. `Main._on_quit()` 无条件调用 `return_to_menu()`，因此“退出游戏”按钮和 `NOTIFICATION_WM_CLOSE_REQUEST` 都被拒绝；
7. `SaveProblem` 的“放弃此存档并新开冒险”只在 `can_discard_saved_run`（`run` 槽读取错误）时可见，`meta` 损坏时不可见。

后果：玩家只能从外部删除 `user://raiddeck/meta.json`/`.bak` 才能继续；这违反“损坏档不应直接锁死玩家”的存档要求。若只是 `meta` 主档损坏而备份有效，`read_slot` 会恢复；只有主档和备份都不可用或版本不兼容时才会锁死，但这仍是必须处理的边界。

建议：

- 区分“读取失败”和“写入失败”：读取失败且 `phase == IDLE` 时允许退出/回菜单（没有未保存进度可丢）；
- 为 `meta` 损坏提供显式的“重置永久记录”入口（保留损坏文件备份、二次确认、不虚构统计）；或允许在确认后以空 meta 新开一局；
- `Main._on_quit()` 恢复“菜单/空闲状态可直接退出”的行为，或把 `return_to_menu()` 的阻断条件细化为“有活动局或未保存的终局结果”；
- 增加“meta 主档+备份都损坏时仍可退出/重置”的回归用例；同时把 Quit 按钮在不可退出时禁用，避免点击无反应。

### 4.5【P2｜验收口径】`content_scale_size` 用例不等于物理最低窗口，当前“1200×760 已覆盖”的表述偏乐观

位置：[test_chapter_ui.gd:661](../../tests/test_chapter_ui.gd:661)、[test_battle_ui.gd:646](../../tests/test_battle_ui.gd:646)

测试：

```gdscript
root.content_scale_size = value
root.size = value
```

临时探针确认：

```text
初始：root.size=(100,100) visible=(1440,900) content_scale_size=(1440,900)
只改 root.size：visible 仍为 (1440,900)
再改 content_scale_size：visible 变为 (1200,760)
```

`canvas_items` 拉伸下，物理窗口缩放到 1200×760 时逻辑视口仍是 1440×900；测试的 1200/1280 用例实际是在模拟“另一种基准视口”，不是“最小物理窗口”。因此：

- 这些用例仍能验证可变逻辑视口下的布局（如果产品打算支持），但不能单独作为“1200×760 最低窗口已验收”的证据；
- 真实最低窗口还需要按缩放后的屏幕坐标检查弹窗和字体，或把 `Main` 放进固定 1200×760 的容器做布局测试；
- 若产品明确固定 1440×900 逻辑视口，则应把 `_set_logical_size` 用例改名为“逻辑视口变化鲁棒性”，并补真实物理窗口/容器用例。

这次测试确实抓到了 4.2 的真实算法问题，但也放大了“最低窗口”结论的覆盖范围，建议在施工记录中修正表述。
