## 3. 主要发现

### 3.1【重要｜第二阶段设计前置】事件与遗物扩展机制不足

位置：[battle_events.gd](../../scripts/core/battle_events.gd:5)、[battle_events.gd](../../scripts/core/battle_events.gd:27)、[battle_engine.gd](../../scripts/core/battle_engine.gd:166)

现状：

- `RULE_HANDLERS` 是固定常量表，只注册三个被动：`_first_damage`、`_first_shield`、`_first_heal`；`notify()` 通过 `call(method, context)` 无条件调用。
- `context` 是借用的普通 `Dictionary`，内含**活引用**的单位字典；事件响应方可以在结算中途修改单位状态，当前没有“允许修改哪些字段、是否可取消、嵌套触发顺序”的契约。
- `preview()` 用 `get_script().new(data)` 克隆，但只复制 `state` 和 `rng`，**没有复制 `events` 实例**；若第二阶段把遗物注册在 `events` 上，预览将与实际结算不一致。

风险：

- 第二阶段要接 35+ 遗物、职业被动、Boss 机制。按现在的固定表扩展，只能把所有遗物处理函数写进 `battle_events.gd` 并全量调用，无法表达“本场战斗只拥有某几件遗物”。
- 活引用上下文 + 无契约，容易出现“遗物在伤害通知里加盾，随后本次伤害重复结算”这类顺序问题。
- 预览不一致会直接违反现有“预览与实际一致”的验收要求（`test_battle_rules`、`test_battle_sim` 都依赖该性质）。

建议：在进入第二阶段前，先确定统一 `BattleContext`（source/target/card/amount/cancelled 等）与实例级注册表；明确响应方只能通过受控接口修改状态；把注册表纳入预览克隆；并为“多遗物同触发顺序”补用例。

### 3.2【重要｜第二阶段设计前置】预览依赖整体状态克隆

位置：[battle_engine.gd](../../scripts/core/battle_engine.gd:160)

现状：

```gdscript
var clone: RefCounted = get_script().new(data)
clone.state = state.duplicate(true)
clone.rng.seed = rng.seed
clone.rng.state = rng.state
clone._execute_card(...)
```

问题：

- 子类或后续新增的战斗状态（遗物集合、姿态、全局计数器、战斗上下文）不会自动进入克隆；预览可能漏算或错算。
- 每次悬停都深拷贝完整状态并执行一次完整结算；当前规模没问题，但接入 35 遗物、召唤物和复杂 Boss 后，悬停预览的成本和副作用面会扩大。
- 若未来某个效果在结算中修改 `data`、静态缓存或外部单例，预览会污染真实状态。

建议：把战斗状态收敛为可显式复制的数据对象（或提供 `copy_for_preview()`），让预览走同一条纯计算路径；为带遗物的预览补“预览前后真实状态与 RNG 完全不变”的断言。

### 3.3【重要｜存档前置】奖励洗牌发生在 `battle_ended` 内，共享 RNG 的推进时点未定义

位置：[run_manager.gd](../../scripts/core/run_manager.gd:126)、[battle_engine.gd](../../scripts/core/battle_engine.gd:419)

现状：`battle_ended` 在 `_publish()` 内发出，此时 `_publishing == true`；`RunManager._on_battle_ended()` 里调用 `battle.shuffle(pool)` 洗奖励池，而 `battle.rng` 就是 `run.rng`（`start()` 时传入的同一对象）。也就是说，**在 `settled` 快照发布之后，运行级 RNG 又被推进了一次**。

影响：

- 当前模拟把整局跑完再比较，所以可复现测试通过。
- 第二阶段接存档时，如果存档在 `settled`/回合结束时保存 RNG 状态，奖励洗牌的推进点不在存档内，读档后重算会与不读档的结果不同。
- 反过来，如果存档在领取奖励后保存，则又可能重复推进。

建议：明确“运行级 RNG 的唯一推进点”，把奖励池生成移到一个确定的状态转换（例如 `RunManager` 的战后结算方法），不要让游戏状态推进依赖展示信号；在存档设计中记录并测试“同种子/同操作序列读档后结果一致”。

### 3.4【重要｜验收可信度】无头模式下尺寸用例没有真正改变视口

位置：[test_battle_ui.gd](../../tests/test_battle_ui.gd:445)

现状：用例设置 `root.size = Vector2i(1280, 800)` 后，用 `app.get_viewport_rect()` 作为边界检查控件是否越界；但探针显示无头模式下 `get_viewport_rect()` 始终是 1440×900（`canvas_items` 拉伸使逻辑视口保持基准尺寸）。因此：

- 1280×800 与 1440×900 两轮检查的是同一个视口；
- “Unit remains inside viewport at supported size”实际只覆盖了 1440×900；
- 施工记录中“1280×800／1440×900 下关键控件边界已有通过的 UI 自动用例覆盖”这一表述偏乐观。

建议：改为显式设置并断言 `root.size`/`root.content_scale_size`/测试容器尺寸确实变化，再检查布局；或用一个固定 1200×760 的父容器承载 `Main` 做真实布局测试。该分辨率仍建议保留人工画面复核。

### 3.5【一般】自施驱散牌在 UI 上无法选择状态（当前内容未触发）

位置：[battle_view.gd](../../scripts/ui/battle/battle_view.gd:261)、[battle_view.gd](../../scripts/ui/battle/battle_view.gd:269)

现状：目标为 `self` 的卡牌走“施放”按钮路径：

```gdscript
func _on_cast_pressed() -> void:
    _play(selected_caster)
```

`_play()` 不传 `chosen_status`。如果未来出现“目标 self + 驱散 + 目标身上多个可驱散状态”的卡牌，`validate_play()` 会返回 `error.dispel`，玩家无法通过 UI 选择状态（因为 `_on_unit_selected()` 在 `cast_button.visible` 时直接返回）。

当前 `first_aid` 目标是 `ally`，点击队友/自己会走 `_on_unit_selected()` 的驱散选择分支，所以现有内容不受影响。

建议：让“施放”路径复用同一套状态选择流程；或在配置校验中暂时禁止“self 目标 + dispel”组合，直到 UI 支持。

### 3.6【一般】奖励回执失败时可能软锁

位置：[main.gd](../../scripts/ui/main.gd:65)、[reward_panel.gd](../../scripts/ui/run/reward_panel.gd:40)

现状：`RewardPanel._on_claim()` 先 `_mark_submitted()` 再 `claimed.emit()`；`Main._on_claimed()` 忽略 `run.claim_reward()` 的布尔返回值。若因批次/阶段/候选不匹配导致领取失败：

- 面板保持 `_submitted = true`，按钮和跳过全部禁用；
- `run.phase` 仍是 `REWARD`，没有新的 `changed` 信号；
- UI 进入无法继续的状态，只能重开。

当前正常流程下失败概率很低，但这是“展示层先提交、核心层后校验”的典型脆弱点。建议检查返回值，失败时恢复面板或重新渲染；补一个“伪造过期 token 领取失败后仍可操作”的用例。

### 3.7【一般】最终战金币被忽略

位置：[run_manager.gd](../../scripts/core/run_manager.gd:107)

现状：最终胜利在 `gold += encounters[stage_index].gold` 之前直接进入 `WON`。当前最终遭遇 `outpost_trial` 的 `gold` 为 0，所以无感；未来若给最终战配金币，会被静默丢弃。

建议：要么在最终战也结算金币，要么在校验中断言最终战 `gold == 0` 并写明设计意图。

### 3.9【一般】文档与验收入口不一致

位置：[代码开发规范.md](./代码开发规范.md:106)、[accept_phase_one.py](../../tools/accept_phase_one.py:88)

- 规范写“统一验收入口为 `python tools/accept_phase_one.py`”，但 argparse 要求必须二选一：`--static-only` 或 `--godot <Path>`；裸跑会以退出码 2 打印 usage。建议改文档为 `--static-only`，或给脚本一个默认静态模式。
- [原始开发规范](../../docs/DEVELOPMENT_SPEC.md) 仍描述 EventBus、ActionQueue、1000 场压测、90–120 张卡；当前实现按确认稿走了不同架构。建议在原始规范顶部加“已被确认稿/重建规范替代”的提示，避免后续 Agent 误读。
- 原始规范要求 1000 场战斗压测；当前验收是 32 种子 × 双跑，每个种子实际到达 3 场战斗（约 192 场）。施工记录已如实说明“不把种子数冒称已完成战斗数”，但生产前仍建议扩大 soak 测试并统计胜率/回合数。

### 3.10【建议】测试覆盖缺口

现有用例质量总体较高（结构化结果、错误日志、非零退出、空断言、源码指纹都有防误报设计），但仍建议补：

1. 敌方意图附加状态的实际应用（`sentry.2` 的 weak、`cultist.1` 的 poison）；目前主要由模拟间接覆盖，没有直接断言。
2. “手牌全不可出时结束回合不弹确认”的路径。
3. 奖励候选的唯一性、按双同职业阵容过滤的边界。
4. 携带过期 token 的领取/跳过失败路径，以及失败后的 UI 可恢复性。
5. 最终战金币、Boss 打断免疫连续两次阈值、状态衰减比例分配的可读断言（后者已有直接用例，但可再加多来源余数分配）。
6. 对话窗主题、实际输入路由（原生窗口 vs 嵌入窗口）和人工画面；这些是 `gui_embed_subwindows=true` 的测试无法替代的。

另外，`test_battle_rules` 多处采用“先改 `data.books`，测试末尾恢复”的写法（如 [test_battle_rules.gd](../../tests/test_battle_rules.gd:111)）；断言失败会跳过恢复，导致后续用例在污染数据上运行。建议改成 `try/finally` 式的恢复，或每个用例重新加载数据。

### 3.11【建议】UI/日志细节

- 每个敌人意图都显示 `ui.not_immune`（“无打断免疫”），包括没有打断机制的普通怪；信息噪音，建议只在 `immunity > 0` 时显示或改文案。
- `ui.intent` 模板固定包含 `{status} {stacks}`，无状态意图会留下空白；建议拆成有/无状态两套模板。
- 非纯打断牌（如盾牌猛击）对“已被本回合打断”的敌人仍会记录 `interrupt_failed`，语义上更像“已经打断过”，不是“抗性失败”；建议区分原因。
- 牌堆查看同时列出“本局牌组”和抽/手/弃/消耗/暂移区，同一副本会出现两次；建议标注“牌组总数”和“本场分布”，避免玩家误读。

## 4. 代码亮点

- **无头核心干净**：`scripts/core` 全部 `RefCounted`，不依赖场景树；战斗可脱离 UI 运行，符合第一阶段的核心约束。
- **数据驱动与校验闭环完整**：XLSX → JSON → 运行时加载 → 卡面/预览/日志全部走同一份定义；`config_contract.json` 约束结构，`export_data.py` 与 `game_data.gd` 双重校验，`_source` 可追溯到源表行。
- **随机与预览纪律好**：同种子可复现；预览使用独立克隆，不改真实状态、不推进真实 RNG；`test_battle_sim` 对预览纯读和卡牌守恒做了双跑比对。
- **结算边界考虑细致**：实际扣盾扣血计仇恨、治疗只计实际恢复、状态多来源按贡献分配、死亡清理、打断免疫、发布期间防重入，均有明确实现和用例。
- **验收工具可信**：每套测试输出结构化标记；解析错误、非零退出、超时、空断言、重复结果都判失败；记录源码指纹，防止检查期间源码变化。
- **导出原子性**：先整组暂存、`fsync`、再逐文件替换，失败回滚；混合批次由运行时拒绝。

`test_boss_rules` 的失败发生在 `restore()` 本身；由于施工仍在进行，`battle_engine.gd` 的快照/恢复逻辑可能尚未完成，需以最终版本复核，暂不把它当作缺陷结论。
